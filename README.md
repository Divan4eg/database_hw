# Домашнее задание к занятию "`Базы данных, их типы`" - `Первушин Дмитрий`

### Задание 1. СУБД

Кейс

Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

1.1.* Хеширование стало занимать длительно время, какое API можно использовать для ускорения работы?

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.

1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это реализовать?

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.

1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД логистов?

1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?

Приведите ответ в свободной форме.

### РЕШЕНИЕ 1

1.1. Реляционная СУБД (например, PostgreSQL), т.к. они обеспечивают строгую структуру данных, поддерживают транзакции и ACID-свойства, что критично для финансовых операций.

1.1.* СУБД Redis, т.к. она поддерживает быструю работу с хэшами и может существенно ускорить процесс.

1.2. Для лендингов: NoSQL (например, MongoDB). Для CRM: Реляционная СУБД (например, PostgreSQL) или NoSQL, в зависимости от требований.
Причины:
Лендинги часто имеют неструктурированные или полуструктурированные данные, что делает NoSQL подходящим вариантом.
Для CRM, если требуется сложный анализ и транзакции, реляционная СУБД будет предпочтительнее. Если гибкость и масштабируемость важнее, то NoSQL также подойдет.

1.2.* Теоретически возможно использовать одну СУБД (например, MongoDB).

1.3. Реляционная СУБД (например, PostgreSQL), т.к. они хорошо подходят для хранения структурированных данных с чёткими связями и иерархией.

1.3.* Да, реляционную СУБД из пункта 1.1

1.4. Графовая СУБД, т.к. они специально разработаны для работы с данными, имеющими сложные связи, что делает их эффективными для задач маршрутизации и распределения ресурсов.

1.4.* Можно подключить отдел закупок к графовой базе данных, если задачи закупок тесно связаны с логистикой. Однако если у отдела закупок уникальные требования к хранению и обработке данных, может быть разумным создать отдельную СУБД.

1.5.* Мультимодельная СУБД (например, ArangoDB), т.к. она поддерживает графовую, реляционную и ключ-значение модели данных, что позволяет эффективно моделировать и работать с различными типами данных и связей между ними. 

### Задание 2. Транзакции

2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы транзакция завершилась успешно. Ориентируйтесь на шесть действий.

2.1.* Какие действия должны произойти, если пополнение счёта телефона происходило бы через автоплатёж?

Приведите ответ в свободной форме.

### РЕШЕНИЕ 2

1. Инициация платежа пользователем (выбор способа пополнения, ввод номер телефона и сумму платежа)

2. Проверка данных и валидация (проверка корректности номера телефона, проверка достаточности средств на платёжном инструменте)

3. Блокировка средств (платёжная система временно блокирует сумму на счёте пользователя)

4. Обработка платежа

5. Зачисление средств и фиксация транзакции (оператор увеличивает баланс номера на указанную сумму, генерируется уникальный ID транзакции, данные записываются в базу оператора и платёжной системы, средства окончательно списываются с платёжного инструмента пользователя)

6. Уведомление сторон (пользователь получает подтверждение с деталями платежа, оператор обновляет баланс в личном кабинете пользователя, платёжная система фиксирует завершение операции в истории транзакций)

Пополнение через автоплатёж
1. Настройка автоплатежа (пользователь заранее указывает номер телефона, порог баланса, сумму пополнения, платёжный инструмент)

2. Мониторинг баланса (система автоматически отслеживает остаток на счёте с заданной периодичностью, при достижении порога запускается процесс пополнения)

3. Автоматическая проверка условий (cистема убеждается, что номер активен? на карте достаточно средств)

4. Бесшовная авторизация

5. Автоматизированное проведение платежа

5. Пост‑уведомление

### Задание 3. SQL vs NoSQL
3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL.

3.1.* Какие, на ваш взгляд, преимущества у NewSQL систем перед SQL и NoSQL.

Приведите ответ в свободной форме.

### РЕШЕНИЕ 3

Преимущества SQL-систем
1. Строгая согласованность данных (ACID)
Это критично для финансовых систем, учёта и других сценариев, где недопустимы расхождения.
2. Структурированные данные и жёсткая схема
В SQL заранее определяется схема БД, что в свою очередь, обеспечивает целостность данных, упрощает отладку и поддержку.
3. Мощный язык запросов (SQL)
В NoSQL запросы часто ограничены ключевыми операциями или требуют написания кода.
4. Развитые инструменты администрирования и мониторинга
SQL‑системы имеют встроенные средства бэкапа/восстановления, детализированные логи, графические интерфейсы.
5. Широкая экосистема и совместимость
NoSQL‑системы чаще «заточены» под узкие задачи и менее универсальны.

Преимущества NewSQL‑систем перед SQL и NoSQL
NewSQL объединяет лучшие черты SQL и NoSQL:

1. Масштабируемость + ACID
Горизонтальное масштабирование (как в NoSQL) без потери строгой согласованности (как в SQL).
2. Высокая производительность при транзакционных нагрузках
3. Глобальная распределённость
Поддержка мультирегиональных развёртываний с синхронной репликацией.
4. Совместимость с SQL
5. Самовосстановление после сбоев.
6. Динамическое перераспределение нагрузки.
7. Встроенные механизмы резервного копирования без остановки сервисов.

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.

На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?

Приведите ответ в свободной форме.

### РЕШЕНИЕ 4

Критерии выбора СУБД
1. Тип данных и структура.
2. Объём данных и нагрузка.
3. Типы запросов.
4. Требования к производительности.
5. Масштабируемость.

Выводы
1. Для пакетной обработки больших объёмов данных с акцентом на масштабируемость и отказоустойчивость - Hadoop. 
2. Для задач, требующих высокой скорости обработки (аналитика, машинное обучение) - Spark.
3. Для потоковой обработки в реальном времени с минимальной задержкой рассмотрите  - Flink или Storm.
